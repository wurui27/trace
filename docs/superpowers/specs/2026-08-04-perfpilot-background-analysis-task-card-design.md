# PerfPilot 后台分析任务卡设计

- 日期：2026-08-04
- 状态：交互设计已确认，待书面规格复核
- 适用范围：本地桌面网页版本，并保持生产 API 可迁移性
- 依赖设计：`2026-08-04-perfpilot-local-multiround-report-design.md`、`2026-08-04-dashboard-latest-report-entry-design.md`

## 1. 背景与问题

当前“新建分析”弹窗承担了创建分析、上传输入、等待 SmartPerfetto、等待 PerfPilot AI 和等待最终报告的完整生命周期。前端 `submitTraceAnalysis` 在分析进入终态前不会返回，因此用户上传 Trace 后只能一直停留在弹窗中。

现有弹窗的“取消”只会中止浏览器请求并关闭弹窗，不会停止后端任务、SmartPerfetto 运行或 AI 调用。主界面也只能查询已有最终报告，无法恢复和展示正在运行的分析。刷新网页后，用户看不到后台任务是否仍在执行。

本设计把“上传输入”和“等待分析结果”拆成两个阶段：弹窗只负责提交输入；后台任务的真实状态、失败、完成和取消统一由主界面任务卡承载。

## 2. 目标

1. 所有必需文件上传并由 API 接受后，立即关闭“新建分析”弹窗。
2. SmartPerfetto、PerfPilot 三轮 AI 和报告生成继续在后台运行。
3. 主界面展示当前分析、真实阶段、已用时间和诚实的耗时提示。
4. 刷新网页或离开后返回主界面，仍能从后端恢复同一任务。
5. 用户二次确认后可以真正停止后端分析，而不只是关闭前端界面。
6. 分析完成后，任务卡自动变为“查看最终报告”入口。
7. 当前本地调试阶段，同一团队同一时间最多存在一个非终态分析。
8. 不重新引入演示数据；没有分析时保留完整仪表盘结构并显示空值。

## 3. 非目标

本轮不实现：

- 多任务并行和任务队列管理界面；
- 根据历史样本预测精确剩余时间；
- 移动端专用布局；
- 浏览器关闭后由前端继续执行任务；
- 自动删除已完成或失败的分析；
- 修改 SmartPerfetto 或 Android Memory 内核源码。

后台执行由 API 和内核进程负责，浏览器只负责提交、查询和操作任务。

## 4. 方案选择

比较过三种方案：

1. **后端权威任务卡（采用）**：上传完成后返回分析编号，主界面从 API 查询活动任务并轮询状态。刷新后可恢复，并能实现真实取消。
2. **浏览器本地状态**：把分析编号保存到 `localStorage`。实现较快，但清理浏览器数据、换浏览器或请求丢失后无法恢复，也无法证明后端是否真正取消。
3. **独立进度页面**：上传后跳转到详情页。状态清晰，但不符合用户要求的“弹窗消失、主界面显示正在分析”。

采用方案 1。API 是任务状态唯一事实来源，前端不自行推断完成或取消。

## 5. 用户交互

### 5.1 提交阶段

“新建分析”弹窗继续负责：

1. 选择分析类型和文件；
2. 本地格式、大小和必填项校验；
3. 创建分析；
4. 上传文件并完成服务端校验；
5. 提交后台分析。

弹窗可以显示文件校验和上传进度，但不等待 SmartPerfetto 或 AI 完成。最后一个必需输入成功 finalize、API 返回分析编号和非终态分析状态后，弹窗立即关闭并通知主界面刷新活动任务。

上传失败时弹窗保持打开，显示稳定、可执行的错误信息，并允许重试。上传尚未被 API 接受前关闭弹窗，不显示“正在分析”。如果服务端已经创建分析，前端在用户取消上传时尽力调用同一个后端取消接口，避免遗留长期占用名额的 `creating`、`created` 或 `uploading` 任务。

### 5.2 主界面任务卡

活动任务卡位于“性能总览”标题区下方、现有“最新分析报告”入口上方。仪表盘的结论、核心指标、重点问题和可信度区域继续保留；没有最终结果时显示现有空值，不使用正在处理的数据填充结论。

任务卡展示：

- 标题“正在分析”；
- 当前阶段：准备输入、SmartPerfetto 解析、PerfPilot AI 分析或生成报告；
- 已用时间；
- 固定提示“通常需要 3–8 分钟，复杂 Trace 可能更久”；
- “查看详情”入口，指向 `/analyses/{analysis_id}`；
- 次级操作“取消分析”。

界面不显示由前端计算的虚假百分比，也不承诺精确剩余分钟数。阶段状态来自 Analysis 响应中的真实 `stages` 和 `ai_rounds`。

活动任务存在时，“新建分析”按钮变为不可重复提交的“查看当前分析”入口。即使两个浏览器标签页同时提交，后端的单活动任务约束仍是最终保护。

### 5.3 完成、失败与取消

- `completed` 或 `partially_completed`：任务卡停止轮询，主操作变为“查看最终报告”；有部分结果时明确标记“部分证据不足”。
- `failed`：任务卡显示失败阶段和安全错误摘要，并提供“重新分析”。
- 用户点击“取消分析”：先显示确认对话框，说明会停止当前内核和 AI 工作；确认后按钮变为“正在取消…”并禁用重复提交。
- 只有 API 返回权威 `canceled` 后，界面才显示“分析已取消”。取消结果保留三秒，随后回到完整空数据仪表盘。
- 如果分析在取消请求生效前已经完成，完成状态优先，保留报告并提供打开入口。

## 6. 前端数据流

现有提交函数拆成两个职责：

1. `enqueueTraceAnalysis` 完成鉴权、哈希、创建分析、上传和 finalize，随后立即返回 `{ teamId, analysis }`；
2. 主界面活动任务组件查询和轮询分析状态，不由上传弹窗等待终态。

主界面加载时先读取当前用户和团队，再查询当前活动分析。上传组件通过成功回调把新分析编号通知主界面，从而立即显示任务卡；随后所有更新仍以 API 响应为准。

轮询沿用现有两秒基础间隔和有界退避策略：

- 正常响应时每两秒刷新；
- 暂时网络错误时保留最后一次有效状态并显示“连接中断，正在重试”；
- 连续错误使用有上限的指数退避；
- 恢复连接后继续同一分析，不新建任务；
- 进入终态后停止轮询。

前端不依赖 `localStorage` 恢复任务。刷新后通过活动任务查询恢复；已进入终态但刚完成的任务由最新报告接口接管。

## 7. API 契约

### 7.1 查询活动分析

扩展团队分析列表接口：

```text
GET /v1/teams/{team_id}/analyses?status=active&limit=1
```

`status=active` 表示查询以下所有非终态：

```text
creating, created, uploading, queued, scheduled, running, analyzing
```

接口按创建时间倒序返回当前团队的分析摘要，响应继续使用现有 `schema_version` 和 `analyses` 数组。实现时把 `report_available` 参数改为可选：`status=active` 与 `report_available` 不能同时显式提供；两个参数都省略时仍按 `report_available=true` 处理，保持现有客户端兼容。

所有查询执行现有团队授权和租户隔离。禁止返回其他团队的活动任务。响应设置 `Cache-Control: no-store`。

### 7.2 取消分析

新增 CSRF 保护接口：

```text
POST /v1/teams/{team_id}/analyses/{analysis_id}/cancel
```

请求不需要业务正文。响应返回最新 Analysis 视图，并增加可选的 `cancel_requested_at`。取消处理中，Analysis 保持原有非终态，`cancel_requested_at` 表示服务端已接受请求；这样无需新增 `canceling` 枚举和数据库状态迁移。前端据此显示“正在取消…”。

- 新取消请求被接受：返回 `202 Accepted`；
- 已经 `canceled`：幂等返回 `200 OK`；
- 已经完成、部分完成或失败：返回 `200 OK` 和实际终态，不覆盖结果；
- 分析不存在或不属于当前团队：沿用安全的 `404`；
- 请求在服务端接受前失败：返回稳定可重试错误，不写 `cancel_requested_at`，前端恢复取消按钮；
- 请求已经返回 `202` 后：服务端拥有把任务收敛到终态的责任，后续内核暂时故障由服务端重试，前端继续显示“正在取消…”，不能伪造 `canceled`。

### 7.3 单活动任务约束

创建分析时，服务端在当前团队范围内原子检查非终态分析。已有活动分析时不创建新任务，返回稳定冲突码 `analysis_already_active`、HTTP `409` 和已有 `analysis_id`。前端收到该响应后关闭重复提交路径并恢复已有任务卡。

本地运行时和生产 AnalysisService 必须使用相同语义。前端禁用按钮只是体验优化，不能替代服务端约束。

## 8. 后端取消语义

取消是一个服务端协调动作，不等同于取消浏览器请求。

1. 在原子锁或数据库事务中读取分析；若已终态则直接返回。
2. 写入 `cancel_requested_at`，阻止后续调度新的 SmartPerfetto、Android Memory 或 AI 工作。
3. 如果 SmartPerfetto 已获得运行引用，调用现有 Adapter 的 `cancel(run_ref)`；如果 Android Memory 正在执行，调用其取消能力。
4. 如果 PerfPilot AI 或报告生成正在执行，取消对应协程或 Worker 执行，并阻止开启下一轮。
5. 把尚未终止的阶段收敛到 `canceled`，原子持久化 Analysis 状态。
6. 后续迟到的内核响应或 AI 响应在提交结果前再次检查取消标记，不能把 `canceled` 覆盖为完成。

本地运行时为每个分析保留任务句柄和取消标记，并将取消标记写入现有状态目录。单纯调用 `asyncio.Task.cancel()` 不足以完成取消：必须先尝试停止外部内核，再收敛本地任务和持久化状态。

生产实现复用已有 Job `cancel_requested_at`、引擎 Adapter 取消能力和 Synthesis 取消能力。取消请求必须支持重复调用，且同一个外部运行最多执行一次有效停止操作。

并发规则如下：

- 完成事务先提交：完成结果优先，取消接口返回实际完成状态；
- 取消标记先提交：任何后续完成写入都必须放弃，最终状态为 `canceled`；
- API 进程重启：从持久化取消标记继续收敛，不重新启动已取消任务。

## 9. 错误与恢复

| 场景 | 用户可见行为 | 服务端行为 |
| --- | --- | --- |
| 文件校验或上传失败 | 弹窗保持打开，可修正后重试 | 不启动内核 |
| 上传已接受，后续分析失败 | 弹窗已关闭，任务卡显示失败阶段 | 保存稳定错误码和终态 |
| 状态轮询断网 | 保留最后状态，显示重连提示 | 任务继续运行 |
| 取消请求在服务端接受前失败 | 恢复取消按钮并显示可重试错误 | 不写取消标记，保持真实运行状态 |
| 已接受取消后内核暂时故障 | 继续显示“正在取消…” | 持久化取消标记并有界重试，禁止启动后续阶段 |
| 取消与完成竞争 | 展示 API 返回的实际终态 | 按事务顺序决定结果 |
| 刷新或重新打开网页 | 从活动查询恢复任务卡 | 不新建任务 |
| API 普通重启 | 恢复分析和取消状态 | 不重复运行已完成阶段 |

这里的“API 普通重启”不包括项目现有的清空式 `npm run dev:restart`；该命令按用户既定要求删除本地历史分析数据。

错误提示不得包含令牌、绝对路径、上游原始正文或内部存储坐标。

## 10. 测试策略

### 10.1 前端单元与组件测试

- `enqueueTraceAnalysis` 在最后一个 finalize 成功后返回，不继续等待终态；
- 上传过程中失败时弹窗保持打开，成功接受后立即关闭；
- 主界面加载活动任务并按真实阶段渲染；
- 刷新语义不依赖 `localStorage`；
- 轮询进入完成、部分完成、失败或取消后停止；
- 暂时网络错误保留最后状态并继续重试；
- 取消必须二次确认，请求中禁用按钮；
- API 未返回 `canceled` 前不显示“分析已取消”；
- 完成后“查看最终报告”使用真实分析编号并进入 `/analyses/{analysis_id}/report`；
- 存在活动任务时不能重复提交。

### 10.2 后端单元与集成测试

- 活动分析查询只返回当前团队的非终态任务，并按创建时间排序；
- 现有 `report_available=true` 查询保持兼容；
- 同一团队并发创建只成功一次，不同团队互不影响；
- 在上传、排队、SmartPerfetto、Android Memory、三轮 AI 和报告阶段分别取消；
- 取消调用外部 Adapter，并阻止后续阶段启动；
- 重复取消幂等且不会重复停止同一外部运行；
- 已完成任务收到取消请求时保留报告；
- 模拟取消与完成竞争，验证终态不会被迟到写入覆盖；
- 本地 API 重启后恢复取消状态，不恢复被取消任务；
- 取消和活动查询均验证鉴权、团队隔离、CSRF 与 `no-store`。

### 10.3 浏览器验收

使用真实本地 API 验证：

1. 上传 Trace；
2. 最后一个上传成功后弹窗自动关闭；
3. 主界面立即出现“正在分析”和“通常需要 3–8 分钟”；
4. 刷新网页后仍显示同一任务；
5. 取消时出现确认框，并真正停止后端任务；
6. 重新提交一个任务并等待完成；
7. 任务卡自动出现“查看最终报告”，点击进入真实报告页面；
8. 页面和 API 中不存在演示分析数据。

## 11. 验收标准

1. 用户上传 Trace 后无需停留在弹窗等待分析。
2. 后台分析不依赖浏览器页面持续打开。
3. 主界面始终展示 API 的真实活动任务和阶段。
4. 刷新、路由切换和暂时断网不会丢失任务。
5. 同一团队无法同时创建两个非终态分析。
6. 取消需要二次确认，并停止外部内核、AI 和后续报告工作。
7. 取消、完成竞态不会破坏已完成报告或复活已取消任务。
8. 失败和取消都不会被前端伪装成成功。
9. 完成后可以从主界面直接打开最终报告。
10. 前后端自动化测试、SSR 构建、Lint 和真实浏览器验收全部通过。
