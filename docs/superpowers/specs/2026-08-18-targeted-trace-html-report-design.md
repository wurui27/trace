# 定点 Trace 分析与 SmartPerfetto 原始 HTML 报告设计

**日期：** 2026-08-18
**状态：** 已由用户确认
**范围：** 仅修改桌面端“上传 Trace 分析”及最终报告；真机设备采集流程保持不变

## 1. 目标

本次改动解决四个产品问题：

1. SmartPerfetto 原始报告必须是 SmartPerfetto 自己生成的 HTML，按原始字节保存、展示和下载，不再把 JSON 当作原始报告。
2. PerfPilot 的所有问题判断和优化建议都必须建立在 SmartPerfetto 分析证据上，再结合可信源码上下文给出可执行修改方案。
3. 报告面向不熟悉性能的人员和管理者：主要三条默认展开，其余结论完整保留并可展开；删除“技术附录”。
4. 上传 Trace 分析必须指定目标应用包名，一次只分析一种测试类型，并移除内存证据、APK 等辅助文件入口。

## 2. 已确认的产品决策

| 主题 | 决策 | 明确不做 |
|---|---|---|
| 原始报告 | 保存 SmartPerfetto 原生 HTML 的原始字节 | 不把 JSON 转成 HTML，不展示完整 JSON |
| HTML 来源 | 优先使用 SmartPerfetto `reportUrl`；若该入口不是 HTML，继续定位 SmartPerfetto 自身的 HTML 生成/导出入口 | 不由 PerfPilot 拼装或仿造“原始 HTML” |
| 场景 | 一次分析只对应一个场景、一份原始 HTML | 不做 startup/scroll 多报告集合 |
| 结论来源 | 每条 PerfPilot 结论必须引用 SmartPerfetto 的结构化发现或证据 | 不凭模型常识生成无证据问题 |
| 结论展示 | 最重要三条默认展开，其余全部折叠保留 | 不把报告硬截断为三条 |
| 结论结构 | 问题点、为什么会有这个问题、结合源码判断的根因、修改建议 | 不展示面向开发者的内部流水线字段 |
| 报告标签 | 结论、源码优化、SmartPerfetto 原始报告 | 删除技术附录标签及打印内容 |
| Trace 表单 | 测试类型、包名、Trace、可选补充问题、可选源码工作区 | 删除内存证据、APK、Mapping、Native Symbols、日志 |
| 数据保留 | 新分析成功提交后，删除当前账号此前全部分析数据 | 不删除其他账号数据；提交失败不删除旧数据 |
| 旧数据 | 部署本次版本时清空旧分析数据 | 不兼容旧 JSON 原始报告 |
| 真机采集 | 保持现状 | 本次不修改设备采集、脚本或 Agent 行为 |

## 3. 上传 Trace 分析

### 3.1 表单

右侧“上传 Trace 分析”只保留以下字段：

- **测试类型（必填）**：冷启动、热启动、滑动、其他。
- **应用包名（必填）**：Android application ID，例如 `com.rivotek.mediacenter`。
- **Trace 文件（必填）**。
- **补充问题（可选）**。
- **源码工作区（可选）**。

选择“其他”时，额外显示：

- **测试名称（必填）**：简短描述场景，例如“视频首帧”。
- **测试说明（必填）**：说明执行了什么操作、要分析什么问题、该测试用于验证什么。

“其他”的名称和说明必须作为分析合同的一部分持久化，报告中使用该名称，不能被归类为冷启动、热启动或滑动。

### 3.2 校验

- 包名在浏览器和服务端都必须校验，采用 Android application ID 的闭合格式；空值、路径、命令片段和控制字符必须拒绝。
- “其他”的名称和说明必须非空并有明确长度上限。
- 一次请求只能包含一个 Trace 文件，不能携带已删除的辅助文件种类。
- 旧客户端若继续上传内存证据、APK、Mapping、Native Symbols 或日志，新合同应稳定拒绝，而不是静默忽略。

### 3.3 定点分析

服务端把包名、测试类型以及“其他”说明作为结构化目标传入 SmartPerfetto 分析请求。SmartPerfetto 返回后，PerfPilot 必须验证目标解析结果：

- 证据明确属于目标包名时，才可形成确定性问题结论。
- 证据属于其他应用或无法解析到目标包名时，报告明确写明目标证据不足，不得混入其他进程的问题。
- 源码匹配也必须绑定同一目标包名、当前账号和当前分析。

## 4. SmartPerfetto 原始 HTML

### 4.1 获取

SmartPerfetto 完成分析后，适配器保留结构化结果供 PerfPilot 二次分析，同时获取 SmartPerfetto 自身生成的 HTML：

1. 从受约束的 `reportUrl` 获取报告。
2. 校验响应成功、MIME 为 `text/html`、大小在硬上限内且最终 URL 未越过已配置的 SmartPerfetto 服务边界。
3. 若 `reportUrl` 不提供 HTML，定位并调用同一 SmartPerfetto 服务实际使用的 HTML 生成或导出入口。
4. 如果 SmartPerfetto 本身没有 HTML 生成能力，本任务不得以 JSON 转换结果冒充原始 HTML；应将其作为集成缺口阻止发布。

### 4.2 保存与读取

- HTML 按收到的原始字节保存，不规范化编码、不格式化、不注入样式、不重写链接。
- 私有制品必须绑定当前账号、分析 ID、制品 ID、MIME、字节数和 SHA-256。
- 下载端点返回完全相同的字节和 `text/html`。
- 页面通过隔离的报告容器读取该端点；隔离策略只作用于浏览器执行环境，不修改保存的 HTML。
- 新分析只产生一份 HTML，不再返回场景集合 JSON。

### 4.3 失败边界

- HTML 获取失败不能把 JSON 显示成原始报告。
- HTML 获取使用有界重试；最终仍失败时，分析不得显示为完整成功，必须以稳定的部分完成状态说明“SmartPerfetto 原始 HTML 获取失败”。已经闭合的 PerfPilot 结论可以保留，不能伪造 HTML 补齐成功状态。
- 错误、日志和公开响应不得泄漏 SmartPerfetto 内部 URL、认证信息、本地路径或原始私有字段。

## 5. PerfPilot 二次分析报告

### 5.1 证据链

公开报告的证据链为：

`目标 Trace + 包名 → SmartPerfetto 结构化分析 → PerfPilot 证据闭合 → 可选源码匹配 → 中文优化结论`

每一条 PerfPilot 结论必须：

- 引用至少一个 SmartPerfetto finding、metric 或 evidence 标识；
- 与当前包名和当前测试类型一致；
- 在使用源码根因时引用经过 strong 匹配的源码位置；
- 无源码或匹配不足时明确写“未能从源码确认”，不能伪造文件、行号或 Diff。

### 5.2 单条结论结构

每条结论固定为四段：

1. **问题点**：直接指出发生了什么性能问题。
2. **为什么会有这个问题**：用通俗中文解释 SmartPerfetto 证据所揭示的机制和影响。
3. **结合源码判断的根因是什么**：strong 匹配时指出具体代码根因；否则明确说明尚未从源码确认。
4. **修改建议**：给出可以执行的修改动作和必要的验证标准。

技术术语、包名、线程名、类名、方法名和指标名可保留英文，其余叙述必须使用清晰中文。

### 5.3 主要结论与其余结论

- 服务端保留所有通过证据闭合的结论，不再使用三条总数上限丢弃内容。
- 按严重性、用户影响、证据强度和修复价值确定前三条主要结论。
- 主要三条默认展开。
- 第四条及之后放入“展开其余结论（N 条）”，逐条完整展示相同四段结构。
- 折叠只改变页面展示状态，不能从报告合同或下载内容中删除其余结论。

### 5.4 页面结构

最终报告只保留：

1. **结论**：主要三条和可展开的其余结论。
2. **源码优化**：只展示可信源码定位、修改方案、Diff 和验证建议。
3. **SmartPerfetto 原始报告**：展示原始 HTML，并提供 HTML 文件下载。

“技术附录”组件、标签、打印层和相关入口全部删除。内部指标仍可用于证据闭合，但不以技术附录形式暴露给目标读者。

## 6. 当前账号数据替换

- 分析记录增加或复用不可伪造的账号所有者绑定；不能仅依赖浏览器传入的账号 ID。
- 新分析完成创建、必要文件上传并成功提交后台后，原子地把当前账号此前的全部分析标记为待清理，再删除其报告、原始 HTML、Trace、源码上下文和运行制品。
- 提交前校验失败、上传失败或任务未成功入队时，保留上一份分析。
- 删除范围只包含当前账号，不得跨账号或跨其所属团队的其他成员。
- 服务重启仍按现有部署要求清空分析数据且不备份；用户和 Agent 控制数据不在该清理范围。

## 7. 合同与迁移原则

- 新建 Trace 请求升级合同，加入必填包名、单测试类型以及可选的“其他”名称/说明。
- 原始报告元数据改为 `text/html`，移除 JSON 文档和多场景集合表示。
- 报告合同把“主要结论”与“其余结论”分别建模，同时要求两者都满足 SmartPerfetto 引用闭合。
- 不提供旧 JSON 原始报告兼容读取；部署时清空旧分析数据，避免双合同长期存在。
- 真机设备分析合同不因本次 Trace 上传表单修改而改变。

## 8. 验收标准

### 8.1 原始 HTML

- 使用含非规范空白、属性顺序和 Unicode 表示的 SmartPerfetto HTML，保存、下载后的 SHA-256 和原始字节完全一致。
- 非 HTML、越界 URL、重定向越界、超限、篡改和跨账号读取均被拒绝。
- 页面不再出现“完整 JSON”或 JSON 下载。

### 8.2 结论

- 所有结论都有闭合的 SmartPerfetto 证据引用。
- 三条主要结论默认可见；第四条及之后全部可展开且内容未丢失。
- 每条结论严格包含四个已确认段落。
- 无 strong 源码匹配时不显示路径、行号或 Diff。
- 页面和打印内容都不存在“技术附录”。

### 8.3 Trace 表单与定点分析

- 四种测试类型均可提交；“其他”缺名称或说明时不能提交。
- 包名为空或非法时，浏览器与服务端都拒绝。
- 请求不能携带已删除的辅助文件。
- SmartPerfetto 请求和最终报告都绑定同一目标包名。
- 真机设备采集相关回归测试保持通过。

### 8.4 数据隔离

- 账号 A 新建分析后，A 此前的全部分析数据被删除。
- 账号 B 的分析、报告、HTML 和源码工作区不受影响。
- 新任务提交失败时，账号 A 的上一份报告仍可读取。
- 部署重启后旧分析数据清空，用户与 Agent 注册信息仍存在。

## 9. 实现前必须确认的外部事实

实现第一步必须对实际 SmartPerfetto 服务做只读验证，确认 `reportUrl` 或其原生导出入口返回 HTML。只有确认原生 HTML 生成链路后，才能完成本设计的原始报告部分；禁止用 PerfPilot 自己渲染的 HTML 代替。
