# 完整源码修改方案设计

**日期：** 2026-08-19

**状态：** 待书面确认

**范围：** PerfPilot AI 2.0 输出、AnalysisReport 1.2 写入与桌面端“源码优化”页面

## 1. 目标

源码优化不能只显示一份 Diff，也不能因某个问题不适合自动生成 Diff 就省略修改方案。

本次改造保证：

1. 所有有证据支撑的结论都出现在源码优化结果中。
2. 有可信源码位置且能安全修改时，尽量生成完整 Unified Diff。
3. 不能安全生成 Diff 时，直接给出具体修改方案，不解释“为什么不能生成”。
4. 页面完整保留全部结果，不再截断为三项。
5. 页面固定显示：`修改建议仅供参考，请结合实际业务逻辑审查后再应用。`

## 2. 当前问题

当前链路在三处限制源码修改：

- AI 合同把 `source_fixes` 限为最多 3 项；
- Prompt 告诉模型最多生成 3 份源码修复，并且只要求至少生成 1 份；
- 前端使用 `source.fixes.slice(0, 3)`，即使后端返回更多内容也会丢弃。

因此，只生成一份 Diff 符合当前合同，却不符合产品要求。

## 3. 已确认的产品行为

### 3.1 全量覆盖

“全部”指当前分析投影中所有有 SmartPerfetto 证据的 `confirmed` 或 `suspected` 结论。每条结论必须在源码优化页面对应至少一个可执行动作：

- **Diff 动作**：展示安全、闭合且绑定 strong 源码证据的 Unified Diff；
- **手动方案**：直接展示该结论的具体修改建议，不显示缺少 Diff 的原因。

系统不得因前三条主要结论的展示规则而丢弃其他结论。结论页继续默认展开最重要的三条，其余结论折叠；源码优化页也可默认展示前三组动作，但必须提供“展开其余 N 项”，并完整渲染全部内容。

### 3.2 Diff 生成

AI 对每条结论检查所有 strong 源码引用。每个能安全修改的独立文件或 symbol 都可以生成一份 Diff；同一结论允许有多份 Diff。每份 Diff 继续遵守现有安全规则：

- 只修改一个 `.kt`、`.java` 或 `.xml` 文件；
- 路径、symbol、rule、finding、evidence 和 source ref 必须来自服务端投影；
- 禁止新增、删除、重命名、复制、mode 变更、二进制文件和不安全路径；
- `validation_profile_id` 由 AI 固定返回 `null`，服务端按配置补充；
- 所有 Diff 的 UTF-8 总字节数不得超过 65,536。

源码上下文最多包含 12 个片段，每个片段最多关联 3 个 finding。`source_fixes` 的合同上限从 3 提升到 36，防止模型无界输出，同时覆盖当前可信源码上下文的最大范围。

同一 `(finding_id, relative_path, symbol)` 只能生成一份 Diff。模型应按结论优先级和 source ref 顺序生成；达到总字节上限后，剩余结论使用手动方案。

### 3.3 手动方案

手动方案直接复用已经通过证据闭合和中文校验的 `conclusion.recommendation`。不增加“无法生成原因”“证据不足原因”或内部诊断字段。

以下情况使用手动方案：

- 没有关联源码；
- 源码上下文不可用；
- 匹配强度为 weak 或 none；
- strong 源码片段不适合生成安全的单文件 Diff；
- Diff 超过单项或总字节安全上限；
- Diff 在服务端安全校验中被拒绝。

手动方案可以包含类名、方法名或通用代码示例，但只有 strong 源码证据才能展示真实相对路径、行号、symbol 和 Diff。weak、none 或无源码结果不得泄漏源码坐标。

### 3.4 页面文案

源码优化页面在动作列表上方固定显示：

> 修改建议仅供参考，请结合实际业务逻辑审查后再应用。

页面不显示以下文案：

- “无法生成 Diff 的原因”；
- “没有可安全生成的源码修复”；
- 模型、validator、预算或匹配规则的内部错误说明。

没有 Diff 的结论直接显示标题“修改方案”和具体步骤。

## 4. 合同与兼容性

本次不增加新的报告主版本，也不引入重复的手动方案字段：

- `conclusions[].recommendation` 继续保存每个问题的完整修改方案；
- `source_fixes[]` 只保存通过安全校验的 Diff；
- 前端按 `finding_id` 把 Diff 与 conclusion 组合；没有有效 Diff 时使用 conclusion 的 recommendation；
- 老的 AnalysisReport 1.2 仍可读取。旧报告即使只有一份 Diff，也会为其他结论显示已有修改方案。

新生成候选必须满足以下闭包：

1. 每个 `source_fixes[].finding_id` 必须存在于 `conclusions`；
2. 每份 Diff 必须绑定 strong source ref 和对应 SmartPerfetto evidence；
3. 重复的 `(finding_id, relative_path, symbol)` 被拒绝；
4. 前端按 `conclusions` 顺序展示，不能按 `source_fixes` 数量决定是否遗漏结论。

`top_findings`、优先 recommendations、关键指标和复测项继续最多三条。这个限制只控制摘要，不限制 `conclusions` 和源码动作总数。

## 5. 生成与降级流程

1. 服务端先列出全部必需 conclusion finding ID。
2. 服务端再列出可用于 Diff 的 strong source ref，并要求模型逐项尝试。
3. 模型返回全部 conclusions 和零到多份 source fixes。
4. 服务端验证每份 Diff 的身份、路径、内容和总预算。
5. 安全 Diff 进入报告；没有安全 Diff 的结论自动使用其 recommendation。
6. 前端按结论顺序组合并展示所有动作。

一份不安全 Diff 不能进入报告，也不能让对应结论消失。若首次候选包含无效 Diff，服务端在同一逻辑轮次重试一次，并要求模型删除或修正该 Diff。第二次仍不安全时，服务端丢弃该 Diff，保留已经闭合的结论和手动方案；不得把整份中文总结降级为 `ai_output_invalid`。

## 6. 展示结构

每个问题使用一组源码动作卡片：

1. 问题标题；
2. 一份或多份 Diff 卡片，包含相对路径、symbol、诊断、复测目标和验证状态；
3. 若没有安全 Diff，显示“修改方案”和具体步骤；
4. 不显示缺少 Diff 的原因。

前三组默认显示。第四组及以后放入“展开其余 N 项源码修改”，但仍保存在 DOM、打印内容和下载报告中。

## 7. 验收标准

自动化测试和真实模型验证必须覆盖：

1. 五个有证据结论全部出现在源码优化页面；
2. 超过三份的合法 Diff 能通过后端合同、写入报告并在前端展开；
3. 同一结论的两个不同文件 Diff 都会显示；
4. 没有 Diff 的结论显示具体修改方案，不显示原因；
5. mixed 场景中，Diff 与手动方案的 finding 合集等于全部 conclusions；
6. weak、none、无源码和源码不可用时，方案不包含路径、行号、symbol 或 Diff；
7. 重复 binding、伪造 source ref、越界路径和超预算 Diff 被拒绝；
8. 单个无效 Diff 被剔除后，其他结论和合法 Diff 仍可发布；
9. 页面固定显示“修改建议仅供参考，请结合实际业务逻辑审查后再应用。”；
10. 老的 AnalysisReport 1.2 仍能读取，并为没有 Diff 的旧结论显示手动方案；
11. 当前真实五结论分析重新生成后，源码动作覆盖数为 5，且合法 Diff 不再受三项上限；
12. 报告中文、SmartPerfetto 证据闭合、团队隔离和 strong-only 源码坐标规则保持通过。

## 8. 非目标

本次不自动应用 Diff，不修改用户仓库，不自动提交 Git，不保证所有结论都能生成可直接应用的补丁，也不展示未生成 Diff 的内部原因。系统保证的是：每个有证据结论都有具体方案，能安全生成的 Diff 全部保留。
