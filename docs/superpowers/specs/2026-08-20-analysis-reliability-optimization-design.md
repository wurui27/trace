# 分析可靠性优先优化设计

**日期：** 2026-08-20

**状态：** 待书面确认

**范围：** 分析任务状态、取消、重试、进度、健康检查、异常恢复和可靠性验收

## 1. 背景

PerfPilot 已经覆盖真机采集、远程 Agent、SmartPerfetto、源码关联、AI 中文总结和报告发布。近期故障集中在流程协作，而不是单个算法：

- 分析长时间停留在“等待设备”或“正在分析”；
- 用户点击取消后，远端任务仍可能继续；
- 页面顶部显示分析中，报告区域已经出现结果；
- Agent、SmartPerfetto、源码或 AI 失败时，页面无法说明当前仍在做什么；
- 网络抖动、服务重启或迟到 completion 容易造成重复任务或状态回退；
- 健康接口只返回 API 进程存活，无法反映依赖服务是否可用。

仓库也出现了明显的维护压力。`local_app.py` 已超过 6,700 行，前端 `perfpilot-api.ts` 已超过 3,300 行。可靠性逻辑分散在运行时、Agent task、source task、SmartPerfetto、AI 和前端轮询中。继续堆叠条件判断会扩大状态冲突风险。

本设计先建立可靠性底座，再改善用户可见诊断。它不进行一次性大重构。

## 2. 目标

本次优化必须达到以下结果：

1. 任何活动分析都能说明当前阶段、最近进度、等待对象和可用操作。
2. 任务不会无限重试，也不会在无活动时永久保持“运行中”。
3. 用户在任何阶段都能取消；取消后的迟到结果不能恢复或发布分析。
4. 页面状态、阶段状态和报告状态来自同一服务端权威。
5. 普通进程崩溃或系统服务重启后，未完成任务可以安全恢复。
6. SmartPerfetto、源码读取和 AI 中文总结只要持续产生进度，就不受固定总时长限制。
7. 某个非核心能力失败时，系统保留已经验证的有效证据。
8. 最终用真实 Agent、真实设备、`com.rivotek.mediacenter` 冷启动和匹配源码工作区完成一次端到端验收。

## 3. 非目标

本次优化不包含：

- 新增账号、Agent 审核或源码目录浏览功能；这些已有独立设计和实施计划；
- 修改 SmartPerfetto 原始 HTML；
- 修改 AI 报告内容结构；
- 建设管理员操作记录页面；
- 长期保存分析运行日志；
- 改变“明确执行清空分析数据后重启”会删除分析数据的策略；
- 一次性重写整个 `local_app.py` 或所有服务。

运行日志仍可用于排障，但必须脱敏，并遵守现有清理策略。

## 4. 唯一状态权威

### 4.1 分析主状态

服务端持久化状态是唯一权威。前端、Agent、SmartPerfetto 和 AI 不得各自推断最终状态。

主流程为：

```text
created
  -> waiting_for_resource
  -> capturing
  -> analyzing_trace
  -> analyzing_source
  -> synthesizing
  -> publishing_report
  -> completed
```

任一活动状态可以进入 `cancel_requested`。阶段可以返回可恢复失败、降级或终态失败，但不能跳过状态迁移门禁。

公开终态为：

- `completed`；
- `failed`；
- `canceled`。

源码不匹配、源码不可读或源码 Agent 离线不把完整分析降为 partial 或 failed。Trace 和 SmartPerfetto 成功时，最终状态仍为绿色 `completed`，源码区域单独解释降级原因。

### 4.2 阶段状态

每个阶段持久化：

- `state`：`pending|waiting|running|completed|failed|canceled|not_requested`；
- `started_at`；
- `updated_at`；
- `last_progress_at`；
- `attempt`；
- `max_attempts`，仅用于自动网络重试；
- `failure_code`；
- `failure_message`；
- `retryable`；
- `waiting_for`；
- `progress_summary`；
- `generation`；
- 安全的上游运行 ID、Agent ID 和任务 ID。

阶段进度只保存当前任务需要的信息，不形成长期操作审计。

### 4.3 状态不变量

服务端强制以下不变量：

1. 终态不可回退到活动状态。
2. 旧 generation 的结果不能修改新 generation。
3. `cancel_requested` 之后不能创建新任务、接受新上传或发布报告。
4. 报告可见时，分析必须在同一提交边界进入 `completed` 或已定义的终态。
5. 每个 generation 最多有一份当前报告。
6. 重复 completion、取消和报告发布必须幂等。
7. 前端只展示服务端状态，不通过报告存在性或阶段数组推断主状态。

### 4.4 合同兼容

状态投影使用新的 schema version。现有 1.0、1.1 和 1.2 响应保持精确可读，不向旧版本偷偷增加字段。服务端在迁移完成前继续读取旧持久化状态，并确定性映射到新状态；前端按 schema version 分派。合同、示例、Python 模型和 TypeScript validator 必须在同一提交中更新。

## 5. 阶段执行策略

### 5.1 有明确截止时间的阶段

独占设备和短控制操作保留明确截止时间。

| 阶段 | 初始建议 | 到期处理 |
| --- | ---: | --- |
| 等待 Agent 在线 | 30 秒 | 不创建采集任务，提示 Agent 离线 |
| 等待设备空闲 | 60 秒 | 结束本次分析，提示设备被占用 |
| 等待任务领取 | 30 秒 | 最多重新投递一次 |
| 真机采集 | 用户时长 + 45 秒 | 请求 Agent 停止并关闭采集租约 |
| 报告发布 | 30 秒 | 使用同一 generation 幂等重试 |

这些值必须配置化，并在真实设备验收后校准。

### 5.2 无固定总截止时间的阶段

以下阶段不设置固定总运行时长：

- SmartPerfetto；
- 源码读取和规则匹配；
- AI 中文总结。

只要阶段持续产生有效进度，系统允许它继续运行。系统仍限制并发、内存、磁盘、输出大小、文件数量和请求大小。

有效进度定义如下：

- SmartPerfetto：状态、进度事件、报告片段或心跳发生变化；
- 源码读取：扫描文件数、已读字节数、工程指纹阶段或源码片段数量发生变化；
- AI 中文总结：连接保持活动、流式输出增长或 provider 返回处理中状态。

长时间无活动时，系统按顺序处理：

1. 查询上游权威状态；
2. 尝试恢复连接；
3. 更新 `waiting_for` 和中文提示；
4. 继续等待用户决定；
5. 用户可随时取消。

建议提示阈值：

- 3 分钟无进度：显示“本阶段耗时较长，系统仍在等待结果”；
- 10 分钟无进度：显示“上游暂未返回新进度，可继续等待或取消”。

提示阈值不触发自动失败，也不构成总截止时间。

### 5.3 自动重试

系统只重试明确可恢复的控制操作，例如临时网络失败、502、连接重置和租约协调冲突。

规则如下：

- 每个控制操作最多自动重试一次；
- 重试使用原分析 ID、任务 ID 和幂等键；
- 参数错误、APK 错误、包名错误、源码不匹配和 AI 合同错误不做无限自动重试；
- 用户主动“重新生成 AI”创建新 generation；
- 页面显示是否正在重试、下一次重试时间和剩余次数。

无固定总截止时间的阶段可以恢复连接，但不能因此创建重复上游任务。

## 6. 统一取消

### 6.1 取消顺序

用户点击取消后：

1. API 在持久化事务中写入 `cancel_requested` 和时间；
2. API 立即返回“取消已接受”；
3. Cancellation Coordinator 停止本地协程；
4. 它向 Agent 采集、Agent 源码任务、SmartPerfetto 和 AI 请求发送取消；
5. 它撤销租约、上传授权和下载授权；
6. 它最多等待远端确认 10 秒；
7. 无论远端是否响应，服务端都把分析关闭为 `canceled`；
8. 后台继续清理远端资源，但不得改变用户可见终态。

### 6.2 迟到结果

所有 completion、上传、AI 响应和报告发布在提交前必须再次读取：

- analysis state；
- cancel marker；
- generation；
- task/lease identity。

取消后到达的结果返回稳定冲突，不能写入报告或恢复阶段。

### 6.3 前端取消体验

第一次点击后：

- 按钮立即禁用；
- 状态显示“正在取消”；
- 页面继续读取服务端权威状态；
- 重复点击不创建第二次取消；
- 进入 `canceled` 后停止普通分析轮询；
- 仍可查看取消前已经发布并验证的只读证据，但不能出现取消后生成的新报告。

## 7. 普通重启与显式清理

系统区分两类重启。

### 7.1 普通进程重启

进程崩溃、systemd 重启或容器重启不清数据。启动协调器读取持久化状态并执行：

- 检查 cancel marker；
- 连接 Agent task、source task 和 SmartPerfetto 运行；
- 恢复已持久化 evidence；
- 继续 AI 或报告发布；
- 对已经终止的远端任务关闭本地状态；
- 不重复安装、采集、上传、SmartPerfetto 提交或报告发布。

### 7.2 显式清空后重启

只有明确执行现有 reset 流程时才删除分析数据。它继续保留：

- 用户；
- 团队；
- Agent 和 Agent 申请；
- 源码工作区；
- 服务配置。

reset 不创建备份。删除后，旧分析不恢复。

## 8. 用户可见诊断

### 8.1 分层健康状态

当前 `/v1/health` 只能证明 API 进程存活。新增聚合健康投影，分别检查：

- API；
- SmartPerfetto；
- AI provider 配置与连通性；
- Agent 在线数量和最近心跳；
- 设备 ready/busy/offline；
- 源码工作区可读性；
- DurableTaskSupervisor；
- 存储目录可写性和剩余空间。

总体状态为：

- `healthy`：必要依赖正常；
- `degraded`：部分能力不可用，但仍可完成部分分析；
- `unavailable`：当前无法开始分析。

普通用户只看到自己团队的 Agent、设备和源码能力。管理员可以看到汇总，不看到 token、绝对路径或源码内容。

### 8.2 分析进度投影

服务端返回：

- `analysis_state`；
- `current_stage`；
- `stage_status`；
- `elapsed_seconds`；
- `last_progress_at`；
- `progress_summary`；
- `waiting_for`；
- `available_actions`。

示例：

```text
源码分析
已运行 6 分 24 秒
已读取 1,247 个文件，找到 18 个相关源码片段
最近进度：12 秒前
系统仍在分析，可继续等待或取消
```

### 8.3 错误内容

每个错误必须说明：

1. 发生了什么；
2. 哪个阶段失败；
3. 已经保留哪些结果；
4. 系统是否自动重试；
5. 用户应该检查什么；
6. 用户现在可以执行什么操作。

页面把技术代码放在可复制详情中。诊断信息只包含分析 ID、阶段、错误代码和时间，不包含 token、绝对路径、设备私密标识或源码。

## 9. 组件边界

### 9.1 AnalysisLifecycleCoordinator

它是分析和阶段状态的唯一写入口，负责：

- 校验合法状态迁移；
- 写入阶段进度；
- 检查取消；
- 校验 generation；
- 判断是否可以发布报告；
- 原子关闭报告与分析状态。

### 9.2 Stage Executors

流程逐步拆成：

- `CaptureStage`；
- `SmartPerfettoStage`；
- `SourceStage`；
- `AiSynthesisStage`；
- `ReportPublishStage`。

执行器只接收不可变输入，并返回 completed、degraded、failed 或 canceled。执行器不直接决定整个分析的终态。

### 9.3 DurableTaskSupervisor

它负责：

- 跟踪活动任务和最近进度；
- 发现无活动任务；
- 恢复普通重启前的任务；
- 执行有界控制重试；
- 协调数据库、Agent lease 和远端状态；
- 清理终止任务的残留资源。

### 9.4 CancellationCoordinator

它统一分发取消、撤销权限、拒绝迟到结果并执行后台清理。

### 9.5 HealthAggregator

它聚合依赖状态，向分析创建页、分析进度页和管理员页面提供闭合投影。

### 9.6 前端

前端只展示服务端投影。它不再通过“报告是否存在”或“是否还有 running stage”猜测分析状态。

## 10. 渐进改造顺序

### P0：消除卡住和状态冲突

1. 增加状态迁移门禁；
2. 增加 `last_progress_at`、`waiting_for` 和 `progress_summary`；
3. 替换无限控制重试；
4. 统一取消和迟到结果检查；
5. 原子提交报告与分析终态；
6. 增加普通重启协调器；
7. 增加分层健康状态。

### P1：增强恢复能力

- 单独重新生成 AI，不重新采集 Trace；
- 单独重跑源码阶段，不重跑 SmartPerfetto；
- 单场景失败时保留其他场景；
- 浏览器断网恢复后继续读取同一分析；
- Agent 短暂离线后续租原任务；
- 上传按确认 part 续传；
- 分析创建前检查磁盘空间；
- 检测严重时钟偏差。

### P2：完善交互细节

- 提交后立即禁用按钮；
- 取消后显示“正在取消”；
- 展示最近更新时间；
- 长时间无进度显示黄色提醒；
- 只展示当前阶段可用操作；
- 中文错误与可复制诊断分离；
- 页面刷新后恢复当前分析；
- 报告发布后顶部立即显示绿色“分析完成”；
- 最新报告暂时不可读时，保留上一份已验证报告并显示时间。

### P3：按可靠性边界拆分大文件

完成 P0-P2 后，再将已经稳定的协调器和执行器从 `local_app.py` 移入独立模块。每次只移动一个有测试保护的边界，不进行大爆炸重构。

## 11. 测试策略

### 11.1 故障注入

每个持久化边界都测试：

- 写入前失败；
- replace 后、fsync 前失败；
- 持久化成功但响应丢失；
- completion 重放；
- 取消与完成并发；
- 旧 generation 迟到；
- 浏览器重复点击。

### 11.2 阶段故障

覆盖：

- Agent 短暂离线和长期离线；
- 错误设备和设备忙；
- SmartPerfetto 单场景失败；
- 源码 Agent 离线、源码不匹配和读取中断；
- AI 返回英文、缺字段、重复 Diff 和非法路径；
- 报告写入失败；
- 磁盘写满、权限错误和临时文件残留；
- 服务在每个阶段完成前后重启。

### 11.3 端到端验收

最终验收使用：

- 真实 Agent；
- 真实 Android 设备；
- `com.rivotek.mediacenter`；
- 冷启动；
- 自动启动 `mediacenteractivity`；
- 用户设置的采集时长；
- 匹配的源码工作区；
- SmartPerfetto 原始 HTML；
- PerfPilot 中文总结；
- 多个安全源码 Diff。

验收还要证明服务器 host ADB probe 为零、分析只生成一份当前报告、取消后无迟到发布。

## 12. 验收指标

上线前必须满足：

- 活动分析都有最近进度和等待对象；
- 系统不存在无法解释的无限等待；
- 点击取消后 1 秒内页面进入取消状态；
- 取消后的迟到结果不能发布；
- 同一 generation 最多产生一份报告；
- 页面主状态、阶段状态和报告状态一致；
- 普通重启不重复任务、不丢已持久化进度；
- SmartPerfetto、源码和 AI 持续有进度时可以长期运行；
- 非核心阶段失败时保留已验证证据；
- 所有公开错误和健康响应通过隐私扫描；
- 真实设备端到端验收通过。

## 13. 已确认决策

- 稳定性优先于新增功能。
- 先统一状态、取消和恢复，再拆分大文件。
- SmartPerfetto、源码读取和 AI 中文总结不设固定总截止时间。
- 这三个阶段使用活动检测、状态查询和人工取消。
- 真机采集、等待资源和报告发布保留配置化截止时间。
- 不新增操作记录页面。
- 不改变显式 reset 删除分析且不备份的策略。
